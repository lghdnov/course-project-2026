# ADR-003: Стратегия аутентификации

## Статус

Принято

## Контекст

Необходимо выбрать стратегию аутентификации для социальной сети, интегрированной с экосистемой Matrix. Пользователи уже имеют аккаунты на Matrix-серверах.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Собственная регистрация (логин/пароль)** | Полный контроль | Пользователям нужно запоминать новые учётные данные |
| **Matrix OpenID Federation** | Единый вход для пользователей Matrix, доверие к провайдеру | Зависимость от внешнего сервера |
| **OAuth2 (Google, GitHub)** | Удобство для пользователей | Нет прямой связи с экосистемой Matrix |
| **LDAP / Active Directory** | Корпоративная интеграция | Избыточно для учебного проекта |

## Решение

Выбрана **аутентификация через Matrix OpenID Federation** с генерацией внутренних JWT (access/refresh токенов).

## Обоснование

1. **Единый вход** — пользователи Matrix не создают новые аккаунты, а используют существующие.
2. **Федерация** — работает с любым Matrix-сервером, поддерживающим OpenID.
3. **Внутренние JWT** — позволяют не обращаться к Matrix-серверу при каждом запросе.
4. **Сессии в БД** — возможность отзыва токенов, аудит активности.
5. **Ротация refresh-токенов** — повышенная безопасность при компрометации.

## Решение: Пошаговый процесс аутентификации

| Шаг | Действие |
|-----|----------|
| 1 | Клиент получает `openid_token` от Matrix-сервера |
| 2 | Клиент отправляет токен в `POST /api/v1/auth/login` |
| 3 | Бэкенд верифицирует токен через `/_matrix/federation/v1/openid/userinfo` |
| 4 | Создаётся или получается локальный пользователь |
| 5 | Генерируется внутренний JWT access-токен и криптостойкий refresh-токен |
| 6 | Сессия сохраняется в PostgreSQL |
| 7 | Клиент получает `{access_token, refresh_token, expires_in}` |

## Последствия

- Система зависит от доступности Matrix-сервера для первичной аутентификации
- Для dev-режима реализован `skipVerify` для локальной разработки
- Все сессии хранятся в БД с возможностью отзыва
- Refresh-токены генерируются через `SecureRandom` (64 байта, Base64 URL-safe)
- Access-токены имеют короткое время жизни для минимизации рисков
