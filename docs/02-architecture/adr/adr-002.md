# ADR-002: Выбор базы данных и ORM

## Статус

Принято

## Контекст

Необходимо выбрать СУБД и ORM-фреймворк для хранения данных пользователей, публикаций, комментариев, групп и сессий аутентификации.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **PostgreSQL + JPA** | Надёжность, ACID, мощные типы данных, зрелая экосистема | Необходимость миграций при изменении схемы |
| **MySQL + JPA** | Простота, широкое распространение | Меньше расширенных типов по сравнению с PostgreSQL |
| **MongoDB + Spring Data Mongo** | Гибкость схемы, горизонтальное масштабирование | Отсутствие ACID-транзакций, сложность связей |
| **H2 (для разработки)** | Лёгкость, встроенность | Не подходит для production |

## Решение

Выбрана **PostgreSQL 15+** в качестве основной СУБД и **Spring Data JPA** (Hibernate) в качестве ORM.

## Обоснование

1. **Реляционная модель** — данные системы имеют чёткие связи (1:1, 1:N, M:N), для которых реляционная модель естественна.
2. **ACID-транзакции** — критичны для финансовых операций (подписки, платежи в будущем) и целостности данных.
3. **Мощные типы PostgreSQL** — JSONB для гибких метаданных, ARRAY для тегов, полнотекстовый поиск.
4. **Spring Data JPA** — стандарт де-факто в Spring-экосистеме, снижает объём boilerplate-кода.
5. **Flyway** — управление миграциями схемы БД версионируется вместе с кодом.

## Последствия

- Схема БД нормализована до 3НФ
- Все изменения схемы проходят через Flyway-миграции
- Используются JPA-аннотации (`@Entity`, `@Table`, `@OneToOne`, `@OneToMany`, `@ManyToOne`)
- Для тестов используется TestContainers с реальным PostgreSQL
